# 記事レビュー（最終チェック）

あずきさんの運用フローの **③** にあたる工程。

1. 記事を完成させる
2. あずきさんと一緒に修正する
3. **← ここ。3名によるチェックと改善 ＋ 別の改善案**
4. あずきさんの最終チェック → プッシュ

## 大原則：ファクトチェックを先にやる

**数字が間違っていると、その上に積んだ文章は全部作り直しになる。**
過去に、文章レビューを2周したあとで為替データの誤りが見つかり、章をまるごと書き直す羽目になった。
だから **第1段階のファクトチェックが終わるまで、文章の改善案は一切出さない**。

**この順序を守るかどうかで周回数が3倍変わる。**
2026年8月に2記事を見直したとき、検算をレビューと並行させた記事は**15周**かかり、
先に全数値を検算してからレビューに回した記事は**4周**で収束した。
差は「レビューの往復のあいだに、数字の誤りが新しい文章を生み、それをまた直す」ぶんだった。

**そして「全数値の検算」だけでは足りない。** 同じ2026年8月の景気敏感株の記事は、
全数値が✓だったにもかかわらず**3周目で期間の取り方の誤りが見つかり、記事の半分を書き直した**。
だから **1-0（期間と起点）と 1-0b（比較の土俵）を、数値の検算より先に**置いている。
順番は「①期間と土俵 → ②全数値 → ③文章レビュー」。

## 第1段階：ファクトチェック（自分でやる。サブエージェントに投げない）

対象記事のパスを受け取る。指定がなければ、直近に編集した `content/posts/*.md` を使う。

### 1-0. 期間と起点の妥当性（数値の検算より先にやる）

**個々の数値が全部合っていても、測る期間が偏っていれば結論ごと間違う。**
2026年8月の景気敏感株の記事で、17年リターンを**リーマンショックの底（2009年2月）から**測っていた。
深く落ちたものほど戻りが大きく出るので、景気敏感株が構造的に有利になっていた。
起点を暴落前に戻したら**勝者が入れ替わり、2章・3章・5章・7章とまとめを全面的に書き直すことになった**。
このとき数値の検算はすべて✓で、誤りは1つもなかった。**検算が通ることと、結論が正しいことは別。**

比較の記事では、文章レビューに進む前に次を確認する。

- **起点は暴落の底や天井になっていないか。** 「データがそろう最初の月」を無自覚に使うと、たいてい直近の暴落の底になる
- **起点を5〜10通りずらして、順位が入れ替わらないか。** 入れ替わるなら、その順位は結論の根拠にできない。
  記事に書けるのは「起点を動かしても残ったもの」だけ
- **選べる起点のなかで、いちばん自分に不利（数字が低く出る）ものを主軸にする。** そのうえで「なぜその起点か」を本文に書く。
  これを書かないと、記事が「起点で結論は作れる」と主張した瞬間、その刃が自分に返る
- **終点も1つしか使っていないことを自覚する。** 起点だけ疑って終点を疑わないのは非対称なので、注記で断る

### 1-0b. 比較の土俵（同じく先にやる）

差が出たとき、それが**中身の差ではなく測り方の差**でないかを潰す。

| 見落とし | 実例 |
|---|---|
| **手数料の差** | 業種別ETF（0.352%）とTOPIXのETF 1305（0.066%）で、**年0.29ポイントの差が最初からついていた**。「TOPIXが年0.6ポイント上」の半分がこれだった |
| **片側だけの除外・控除** | ディフェンシブから最下位業種（電力・ガス）を外して「実は互角」と書いた。景気敏感からも最下位を外さないと不公平。**外すなら両側で外して並べる** |
| **母集団の欠けが、どちら側に不利か** | データ不足で商社・卸売を除外 → いちばん伸びた業種なので**景気敏感に不利**。「除外した」だけでなく**「どちらに不利か」まで書く** |
| **実測値と合成値を並べる** | TOPIXの下落幅は実測、比率表の行は2つを混ぜた合成値。合成は深めに出ると自分で注記していたのに、その誤差より小さい2.0ポイント差で勝敗を語っていた |
| **等加重と時価総額加重** | 業種ETFの単純平均とTOPIXは持ち方が違う。差の全部が中身の差ではない |

### 1-1. 全数値の再計算

記事中の数値を洗い出し、**その場でデータを取り直して**照合する。一致しないものは全部報告する。

株価・為替データは Yahoo Finance chart API を使う。

```
https://query1.finance.yahoo.com/v8/finance/chart/{symbol}?range={range}&interval={interval}&events=div|split
```

**必ず守るデータの落とし穴（実際に踏んだもの）:**

| 落とし穴 | 対処 |
|---|---|
| **`JPY=X` の月次データ（`interval=1mo`）は使わない** | 毎年10月がまるごと欠落し、値そのものもずれている（2023-07末を146.10と返すが実際は142.32）。**必ず `interval=1d` を取り、各月の最終値を自分で拾う** |
| `range=max&interval=1d` は銘柄ごとに日付グリッドが崩れる | 長期は `interval=1mo`。ただし為替だけは上記のとおり日次 |
| **`1306.T`（TOPIX ETF）は10:1の分割がデータに記録されていない** | 2016年をまたぐ長期計算が壊れる。TOPIXは **`1348.T`（MAXIS TOPIX）** を使う |
| 日本株の月次と日次で adjclose の配当調整が食い違う | 全銘柄で **`interval=1mo` に統一**して比較する（混ぜない） |
| 上場廃止期間のある銘柄（JAL 2010〜2012 など） | 長期計算から除外し、除外したことと残った比率を記事に明記 |

計算方法の決めごと:
- リターン＝分配込み（`indicators.adjclose[0].adjclose`）、円建ては各時点の為替を掛ける
- リスク＝対数リターンの標本標準偏差（n−1）を年率化（月次なら ×√12、日次なら ×√252）
- **期間や間隔が違う数字を並べない。** 並べるなら「そろわない理由」を注記に書く

検算は「記事の値 → 再計算値 → ✓/✗」の表で出す。✗があれば**その時点で報告し、文章レビューには進まない**。

### 1-2. 表示値どうしの引き算が合うか（読者がやる検算）

**再計算が正しくても、記事に載っている数字どうしで引き算が合わないと読者は止まる。**
端数まで使った値で計算し、表示は丸めた値、というズレが原因。実際に3件見つかった。

| 記事の表示 | 読者の計算 | 実態 |
|---|---|---|
| 13.9% − 11.4% は「2.4ポイント」 | 2.5になる | 実測13.849%を13.9%に丸めていた。**13.8%が正しい** |
| 29.9% − 8.4% は「21.4」 | 21.5になる | 丸める前の値で引いていた |
| 1,315万円の「±15%」が1,513万円 | 1,512になる | 上限だけσ=15.05%、下限は15.0%で計算していた |

```bash
# 記事に出てくる引き算を全部書き出して、表示値どおりに合うか確かめる
node -e 'const c=[["2章カード",15.0,11.4,3.6],["3章カード",13.8,11.4,2.4]];
for(const[n,a,b,d]of c){const x=+(a-b).toFixed(1);console.log(`${n}: ${a}-${b}=${x} / 表記${d} ${x===d?"OK":"×"}`);}'
```

**掛け算も同じ。** 「±667万円」と「±1,334万円」が並ぶなら 667×2 が表示どおりになっているか。

### 1-3. 同じ言葉が2つの数字を指していないか

読者がいちばん混乱するのはここ。実際にあった例:

- 「**分散の効果**」が、3.6ポイント（単純な足し算との差）と2.4ポイント（置き換えたときの差）の両方に付いていた
- 「**1銘柄ずつの平均**」が、27.1%（金額で重みづけ）と25.8%（単純平均）の両方に付いていた

```bash
# 同じ数字が複数の呼び名を持っていないか／同じ呼び名が複数の数字を持っていないか
grep -no "分散の効果\|分散で消えたぶん\|揺れ幅\|ばらつき\|荒さ" 対象.md
```

**呼び分けるか、違いを1行で説明するか、どちらかにする。**
呼び分けたら、記事の全箇所でそろっているか grep で確認する。

### 1-4. 過去記事との突き合わせ

```bash
# 同じ事実の数字ゆれ（保有銘柄数・評価額・過去に出した利回りやリスク）
grep -rn "117銘柄\|1,315万\|5,831万" content/posts/*.md
# 関連記事リンクの実在とタイトル完全一致
grep -oE '\(/blog/[a-z0-9-]+\)' 対象.md | tr -d '()' | sed 's|/blog/||' | while read s; do
  [ -f "content/posts/$s.md" ] && grep -m1 '^title:' "content/posts/$s.md" || echo "❌ $s"; done
```

過去記事と食い違う主張がないかも見る（例：前回「答えは数ではなかった」と書いたのに今回「銘柄数のおかげ」と書く、など）。

### 1-5. 機械チェック

```bash
f=対象.md
grep -nE "——|？。|\?。|^[、。]" $f                      # 禁則（全角ダッシュ厳禁）
grep -n 'grid-template-columns' $f | grep -v 'keep-grid' # 表のkeep-grid漏れ
printf "%s:%s\n" "$(grep -o '<div' $f|wc -l)" "$(grep -o '</div>' $f|wc -l)"  # タグ整合
python3 -c "
import re;t=open('$f').read()
print('正直:',t.count('正直'))                            # 本文1回まで
print('非日本語:',re.findall(r'[Ѐ-ӿ가-힯฀-๿]+',t) or 'OK')"
```

## 第2段階：4名を同時に走らせる

第1段階が全部 ✓ になってから。**Agent ツールを1メッセージで4つ同時に呼ぶ**（並列で走る）。

各エージェントには **記事の全文パス・第1段階の検算結果・下の役割** を渡す。
「改善案は本文の書き換え案まで書くこと」「重箱の隅より、読者が誤解する箇所を優先」と指示する。

### A：数字にうるさい読者
比較の公平さ（同じ土俵か／期間はそろっているか／基準は同じか）、定義のあいまいさ、
「圧勝」「ほぼ消えた」のような**差の大きさに見合わない言葉**、出典のない断定を探す。

### B：反対の立場の読者
その記事で**いちばん不利に扱われている立場**の人になりきる。
（米国ETFの記事なら米国ETF派、日本株の記事ならインデックス派、など。記事を読んで自分で決める）
都合のいい切り取り、傷つく表現、「結局こっちが正解と言っているだけでは」と読める箇所を探す。

### C：校正者
たどたどしい言い回し、重複、話の飛び、ごまもちの会話が本文と矛盾していないか。
**あずきさんが避けたい表現**：全角ダッシュ「——」、「整理してみた」「調べてみた」「〜してみる」の多用、
知らなかったふり（実際は知っていたことを「驚いた」と書く）、しらじらしい自作自演の気づき。

---

### D：「で、結局なにが言いたいの?」と聞く読者

**短くするための役ではない。主張を濃くするための役**。指示はこう渡す。

> この記事を読み終えたあと、内容を知らない人に**1行で説明する**としたら何と言いますか。
> そのうえで挙げてください。
> - その1行を**いちばん強くしている**箇所（2件）
> - その1行に**効いていない、または遠回りさせている**箇所（**4件以上**）
> - 同じことを2回言っている箇所
> 効いていないと判断した理由を必ず添えてください。

Dが出した「主張1行」が記事の意図とずれていたら、**それ自体が最大の指摘**。伝わっていない。

## 長さのルール（全モード共通）

過去にHDV記事が6,977字→14,576字に膨らんだ。原因は情報が増えたことではなく、**留保が増えたこと**だった
（レビューを通した記事は「ただし」「ただ」「なお」が1,000字あたり2.0〜2.2回、通していない記事は0.4〜0.8回）。

| | 扱い |
|---|---|
| **情報**（読者が新しく得をすること） | **本文に足してよい。長くなってよい** |
| **留保**（「ただし〜の場合は違う」「〜とはかぎらない」） | **本文に足さない。注記・表の脚注・免責へ落とす** |

各エージェントには「改善案は**本文に入れるか注記に落とすか**を明記すること」「留保の追加は原則すべて注記」と指示する。

**Dのカット候補は3択で判断する**：削る／注記へ落とす／**残す**。残す場合は理由をあずきさんに報告する。

長さの管理は**読了時間**で見る（記事ページに表示される）。目安は15〜18分。全149記事の中央値は10分。

### 長すぎたときは、削るより分ける

**疲れる原因は長さではなく、主張の本数のことが多い。**
景気敏感株の記事は27分になり、削る作業をしても26分にしかならなかった。
削れる重複が640字しかなく、残りは全部が内容だったから。原因は別のところにあった。

- **数字の密度**：地の文1,000字あたり17.8個（他記事は10.3〜13.6個）。**覚える数値が88種類**あった
- **主張が3本**：①比率に最適点はない ②業種選択が報われない ③起点で結論が変わる。どれが本題か決まっていなかった

**打ち消し表現（ただし・でも・〜ではない）の密度は4.4回/千字で、他記事（3.3〜4.7）と変わらなかった。**
つまり犯人は留保ではなく数字と主張の本数。ここを取り違えると、削る作業が空振りする。

診断はこう出す（数えてから話す。感覚で「長い」と言わない）。

```bash
node -e '
const fs=require("fs");const md=fs.readFileSync(process.argv[1],"utf8").replace(/^---[\s\S]*?\n---\n/,"");
const s=t=>t.replace(/<[^>]+>/g,"").replace(/[#*_`>\-\[\]\(\)!]/g,"").replace(/\s/g,"").length;
const prose=md.replace(/<div class="data-card"[\s\S]*?\n<\/div>\n/g,"").replace(/<div class="conv-wrap">[\s\S]*?\n<\/div>\n\n<\/div>/g,"");
const n=(prose.match(/[−+]?\d+\.?\d*(%|ポイント|倍|万円)/g)||[]);
console.log("表示",Math.round(s(md)/500),"分／地の文",s(prose),"字／数字",n.length,"個・",new Set(n).size,"種類");
' content/posts/対象.md
```

**主張が2本以上あって20分を超えたら、削るのではなく前後編に分ける。**
情報を1つも捨てずに読みやすくできるのはこの方法だけ。`series` と `seriesOrder` を frontmatter に足し、
`lib/posts.ts` の `SERIES_NAMES` に表示名を1行追加すると、前後リンクと目次が自動で出る。
分けるときは各記事の主張を1本にし、つなぎ目（前編末の引き渡し／後編頭の要約3行）と、
またいだ章番号の参照（「次の章の表」など）を必ず直す。

## 公開済み記事モード

すでに公開している記事を見直すときは、上に加えて次を守る。

- **字数の上限は元の+20%まで。** 読者のためになる情報なら足してよい。ただし留保は本文ではなく注記へ。Dのカット候補で相殺できるならなお良い
- URLとタイトルは変えない（SEOの評価が振り出しに戻るため）
- excerptは**記事の外**に出る。記事内で定義した造語（「MY高配当株」など）は使わない
- 過去記事からの**引用文の中は置換しない**。呼び名を統一するときも、引用は当時の言葉のまま

### 検算の期間は「記事を書いた時点」に固定する

**「直近1年」は日々動く。** 今日そのまま再計算すると、記事の数字と合わなくて当然になる。
実際、公開時に11.4%だった数字が5日後には11.5%になっていた。

`range=1y` ではなく `period1` / `period2` で**公開日までに固定**して検算する。

```js
const P1=Math.floor(Date.parse("2025-07-20")/1000), P2=Math.floor(Date.parse("2026-08-10")/1000);
`https://query1.finance.yahoo.com/v8/finance/chart/${sym}?period1=${P1}&period2=${P2}&interval=1d`
```

そのうえで「記事の数字は**書いた時点では正しかった**」と確認できたら、それは誤りではない。直さない。

### 追記を入れるかどうか

記事末の「※YYYY年M月D日追記：〜を訂正しました」は、**読者の判断が変わる訂正のときだけ**入れる。

| 入れる | 入れない |
|---|---|
| 結論が変わる／金額の桁が変わる／事実関係が違っていた | 表示の丸めのズレ（1,513→1,512）、言い回しの修正、説明の追加 |

判断に迷ったらあずきさんに聞く。

## 周回の回し方

**全員が「合格」を出すまで回す。** ただし次の3つを守る。

**1. 反映したら必ず再検算する。**
今回、レビュー中に**わたし自身が持ち込んだ数字の誤りが3件**あった（丸め違い、内訳として成り立たない引き算、集めた銘柄数の取り違え）。
足した文・直した数字は、次の周で必ず1-1〜1-3にかけ直す。**新しく書いたものほど疑う。**

**2. 収束したら止める。**
同じ箇所を3周続けて微調整しているなら、それは収束している。
そのレビュアーへの指示にこう書く:

> 今回も微調整レベルの指摘しか出ないようなら、収束したとみなして合格を出してください。
> 記事全体として、読者がつまずく箇所が本当に残っているかどうかで判断してください。

**3. 各周の指示に、前周の指摘をどう扱ったかを必ず書く。**
「①→反映」「②→見送り（理由）」まで書くと、同じ指摘が繰り返されない。
**見送るときは理由を必ず書く。** 検算で否定できたなら、その数字も添える。

## 第3段階：統合して1つの表で出す

4名の指摘をまとめ、**重複は1件に畳む**。そのうえで自分の判断を添える。

```
| # | 誰 | 指摘 | わたしの判断 |
|---|----|------|-------------|
| 1 | B  | 〜が不公平に見える | 採用推奨：〜と書き換える |
```
